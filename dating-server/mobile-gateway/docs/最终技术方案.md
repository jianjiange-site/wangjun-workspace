## 3. 输入依据和需求继承

### 3.1 已确认信息

- 目标服务是 `mobile-gateway`。
- 服务能力包括外部 API 网关能力、认证登录能力和 BFF 聚合层能力。
- MVP 使用 Spring Boot MVC + JDK 21 虚拟线程。
- 登录 / 注册内化到网关认证域，包括手机号验证码登录、Google 登录、设备号快速登录。
- 网关生成全局 `user_id`，并透传给 user-service。
- 首次注册时，网关必须调用 user-service 的注册 / 初始化流程。
- JWT 由网关签发和验签，仅用于 access token；refresh token 使用 SecureRandom 生成不透明随机串。
- access token blacklist 只使用 Redis。
- 账号、设备、refresh token 需要 PostgreSQL 持久化。
- 网关负责限流、CORS、traceId 注入、REST/gRPC 转换、BFF 聚合和字段裁剪。
- 业务码使用数值型 `Result.code`，`105XX` 表示 Token / JWT / refresh token / blacklist 问题。

### 3.2 用户明确取舍

- 不做内部运维接口。
- 不做动态路由配置平台。
- 不做管理后台。
- 不做 API 开放平台。
- 不做 MQ。
- 不做 PostgreSQL access token blacklist 表。
- 暂不做登录审计表。
- 不做设备号登录后的敏感接口强制绑定手机号或 Google。
- 不做手机号 / Google / 设备号之间的账号绑定、合并或升级。
- 设备号快速登录采用“一个设备一个用户，不同设备不同用户”。
- MVP 固定 `worker-id=1`，不做多实例 worker-id 自动分配。
- MVP 阶段网关自签 JWT 不做 `kid` 和多密钥在线轮换。

### 3.3 模型推断和处理

- BFF 聚合主要服务前端只读页面，不能变成跨服务写事务编排层。
- 业务级权限、业务资源归属、用户资料主数据由下游服务负责。
- 网关是唯一公网入口，需要重点处理认证、限流、超时、降级和可观测性。
- user-service 需要提供按 `user_id` 幂等的注册 / 初始化 gRPC 接口。

### 3.4 进入方案生成风险处理

| 风险 | 处理结论 |
|---|---|
| BFF 聚合边界膨胀 | 明确 BFF 只读聚合，不做跨服务写事务。 |
| user_id 与用户资料边界不清 | 明确网关生成全局 `user_id`，user-service 使用该 ID 初始化用户资料。 |
| 设备号快登低信任 | MVP 保留限流、禁用和幂等，不做强绑定要求。 |
| Redis-only blacklist 风险 | access token 短 TTL，Redis blacklist 校验不可用时 fail closed。 |
| 多实例雪花 ID 冲突 | MVP 固定 worker-id 且只部署一个生成 ID 的网关实例。 |

## 4. 团队技术约束来源

已提供团队技术约束文档，本最终方案遵守以下约束：

- JDK 21。
- Spring Boot 3.3.5。
- Maven。
- MyBatis-Plus。
- PostgreSQL 16。
- Redis 7。
- Nacos 2.4。
- gRPC 1.68.1。
- Protobuf 4.28.3。
- Docker。
- `mobile-gateway` 是唯一公网入口。
- 网关到内部服务只走 gRPC。
- 禁止 FeignClient、RestTemplate 服务间互调。
- 禁止跨服务直连其他服务数据库、Redis key、MinIO bucket。
- 禁止 Seata / XA 分布式事务。
- 事务只放在 Service 层。
- 本地事务内不调用远程 gRPC、不调用第三方 API、不发送 MQ。
- PostgreSQL 表保留内部 `id BIGSERIAL PRIMARY KEY`，但业务操作使用 `xxx_id`。
- Redis key 必须有前缀和 TTL。
- 对外接口和 gRPC 禁止暴露数据库内部 `id`。

约束差异说明：团队文档中存在 `xxx_no` 遗留表述，用户已明确要求业务编号统一使用 `xxx_id`，本最终方案按 `xxx_id` 执行。

## 8. 服务定位和职责边界

### 8.1 负责范围

- REST 外部入口。
- CORS 处理。
- traceId 生成、注入、透传。
- 基础参数校验。
- IP / 账号 / 设备 / 接口维度限流。
- 手机验证码发送、校验、登录 / 注册。
- Google token 校验、登录 / 注册。
- 设备号快速登录 / 注册。
- 设备号快速登录下，一个设备只对应一个用户，不同设备对应不同用户。
- 雪花算法生成 `account_id`、`device_id`、`user_id`、`refresh_token_id`。
- 首次注册后通过 gRPC 调用 user-service 注册 / 初始化流程。
- JWT access token 签发和验签。
- Redis JWT blacklist 校验。
- refresh token 签发、轮换、撤销和持久化。
- 网关认证域账号、设备、refresh token 持久化。
- REST request / response 与 gRPC request / response 转换。
- BFF 只读聚合和一级字段裁剪。
- 统一 `Result<T>` 返回。
- 数值型业务码。

### 8.2 不负责范围

- 不保存用户资料、昵称、头像、关系链等用户主数据。
- 不依赖 user-service 判断登录还是注册。
- 不在网关事务内创建或维护 user-service 用户资料。
- 不直接访问或写入 user-service 数据库。
- 不做手机号 / Google / 设备号之间的账号绑定、合并和升级。
- 不保存帖子、匹配、IM、支付等业务数据。
- 不做业务级权限判断。
- 不做跨服务事务。
- 不直接访问其他服务数据库、Redis key、MinIO bucket。
- 不做内部运维接口。
- 不做动态路由配置平台。
- 不做配置管理后台。

## 9. 总体架构

### 9.1 登录 / 注册链路

```text
AuthController
  -> AuthService
  -> SmsCodeService / GoogleLoginService / DeviceLoginService
  -> GatewayAccountManager.findOrCreateAccount
  -> GatewayDeviceManager.findOrCreateDevice
  -> transaction commit
  -> UserGrpcAdapter.registerOrInitializeUser
  -> JwtService.issue
  -> RefreshTokenManager.save
  -> Redis refresh cache
```

说明：

- 手机、Google、设备号三条登录路径都进入网关认证域。
- 手机和 Google 按账号标识查找或创建 `gateway_account`。
- 设备快登先查 `gateway_device`，同一个 `device_key_hash` 永远返回同一个 `user_id`。
- 首次注册或 `user_register_status=0` 时，调用 user-service 初始化。
- user-service 初始化成功后才签发 token。

### 9.2 请求转发链路

```text
GatewayProxyController / BffController
  -> TraceIdFilter
  -> CorsFilter
  -> RateLimitFilter
  -> JwtAuthFilter
  -> GatewayProxyService / BffAggregateService
  -> XxxGrpcAdapter
  -> XxxGrpcClient
  -> downstream gRPC service
```

### 9.3 数据读写链路

```text
AuthService
  -> Manager
  -> Mapper
  -> gateway PostgreSQL

JwtAuthFilter / RateLimitService
  -> Redis

BffAggregateService
  -> downstream gRPC service
  -> memory assemble
```

## 10. 技术选型

| 用途 | 选型 | MVP 是否必须 | 说明 |
|---|---|---|---|
| Web 框架 | Spring Boot MVC | 是 | 按用户要求，不使用 WebFlux。 |
| 并发模型 | JDK 21 虚拟线程 | 是 | 适合 MVC + 同步 gRPC client。 |
| ID 生成 | 雪花算法 | 是 | 生成全局 `user_id`、`account_id` 等业务 ID；MVP 固定 worker-id。 |
| 数据库 | PostgreSQL 16 | 是 | 持久化账号、设备、refresh token。 |
| ORM | MyBatis-Plus | 是 | 单表操作。 |
| 缓存 / 限流 | Redis 7 | 是 | 验证码、限流、refresh token 快取、JWT blacklist。 |
| 服务发现 | Nacos 2.4 | 是 | gRPC 服务发现。 |
| 内部通信 | gRPC + Protobuf | 是 | REST 转 gRPC。 |
| JWT | Spring Security OAuth2 JOSE / Nimbus JOSE | 是 | RS256 签发和验签。 |
| Google token 校验 | JDK HttpClient + JWKS 缓存 | 是 | 不使用 Feign / RestTemplate。 |
| 容器化 | Docker | 是 | 团队部署约束。 |

虚拟线程约束：

- `spring.threads.virtual.enabled=true`。
- 虚拟线程不替代连接池、deadline、超时和限流。
- gRPC、Redis、PostgreSQL 都必须设置超时和连接池上限。
- 压测必须观察 P95 / P99、DB 连接池、Redis 连接池、gRPC channel 状态。

雪花 ID 约束：

- MVP 固定 `worker-id=1`、`datacenter-id=1`。
- MVP 只部署一个可生成雪花 ID 的 `mobile-gateway` 实例。
- 扩展多实例前，必须设计 worker-id 分配、冲突检测和启动失败策略。

## 12. 数据模型设计

### 12.1 设计原则

- 所有表使用 PostgreSQL。
- 所有表保留 `id BIGSERIAL PRIMARY KEY`，但 `id` 只用于数据库内部排序和排查。
- 所有业务操作使用 `xxx_id`。
- 原则上字段 `NOT NULL`。
- 时间字段使用 `TIMESTAMPTZ`，统一 UTC。
- 持久层不做多表 JOIN。
- 手机号、Google subject、设备原始 ID 使用 HMAC 后落库。

### 12.2 gateway_account

用途：保存网关认证域账号。账号不存在时创建 `gateway_account`，同时生成全局业务用户编号 `user_id`。

```sql
CREATE TABLE gateway_account (
  id BIGSERIAL PRIMARY KEY,
  account_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL DEFAULT 0,
  account_type VARCHAR(32) NOT NULL DEFAULT '',
  account_key_hash VARCHAR(128) NOT NULL DEFAULT '',
  hash_version SMALLINT NOT NULL DEFAULT 1,
  user_register_status SMALLINT NOT NULL DEFAULT 0,
  status SMALLINT NOT NULL DEFAULT 1,
  last_login_at TIMESTAMPTZ NOT NULL DEFAULT '1970-01-01T00:00:00Z',
  created_at TIMESTAMPTZ NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL,
  deleted SMALLINT NOT NULL DEFAULT 0
);

CREATE UNIQUE INDEX uk_gateway_account_id ON gateway_account(account_id);
CREATE UNIQUE INDEX uk_gateway_account_key ON gateway_account(account_type, account_key_hash, deleted);
CREATE UNIQUE INDEX uk_gateway_account_user ON gateway_account(user_id);
```

字段说明：

- `account_type`：`PHONE`、`DEVICE`、`GOOGLE`。
- `account_key_hash`：`HMAC-SHA256(hash_secret_v{hash_version}, normalized_identifier)`。
- `user_id`：网关用雪花算法生成的全局业务用户 ID。
- `user_register_status`：`0` 待调用或待重试 user-service 注册 / 初始化，`1` 已完成。
- `status`：1 正常，2 禁用。

### 12.3 gateway_device

用途：保存设备号快速登录的全局设备身份。MVP 采用“一个设备一个用户，不同设备不同用户”。

```sql
CREATE TABLE gateway_device (
  id BIGSERIAL PRIMARY KEY,
  device_id BIGINT NOT NULL,
  account_id BIGINT NOT NULL DEFAULT 0,
  user_id BIGINT NOT NULL DEFAULT 0,
  device_key_hash VARCHAR(128) NOT NULL DEFAULT '',
  hash_version SMALLINT NOT NULL DEFAULT 1,
  device_name VARCHAR(128) NOT NULL DEFAULT '',
  client_type VARCHAR(32) NOT NULL DEFAULT '',
  status SMALLINT NOT NULL DEFAULT 1,
  last_seen_at TIMESTAMPTZ NOT NULL DEFAULT '1970-01-01T00:00:00Z',
  created_at TIMESTAMPTZ NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL,
  deleted SMALLINT NOT NULL DEFAULT 0
);

CREATE UNIQUE INDEX uk_gateway_device_id ON gateway_device(device_id);
CREATE UNIQUE INDEX uk_gateway_device_key ON gateway_device(device_key_hash, deleted);
CREATE INDEX idx_gateway_device_account ON gateway_device(account_id, deleted);
CREATE INDEX idx_gateway_device_user ON gateway_device(user_id, deleted);
```

字段说明：

- 设备原始标识不落库。
- `device_key_hash + deleted` 全局唯一是有意设计。
- 如果设备已存在，设备快登直接使用该设备绑定的 `account_id`、`user_id`。
- 如果设备不存在，设备快登创建新的认证账号、新的 `user_id` 和新的 `gateway_device`。
- 手机号 / Google 登录不自动合并或升级已有设备快登账号。
- `status`：1 正常，2 禁用。

### 12.4 gateway_refresh_token

用途：持久化 refresh token 会话，支持刷新、撤销和重复使用检测。

```sql
CREATE TABLE gateway_refresh_token (
  id BIGSERIAL PRIMARY KEY,
  refresh_token_id BIGINT NOT NULL,
  account_id BIGINT NOT NULL DEFAULT 0,
  device_id BIGINT NOT NULL DEFAULT 0,
  user_id BIGINT NOT NULL DEFAULT 0,
  token_jti VARCHAR(128) NOT NULL DEFAULT '',
  token_hash VARCHAR(128) NOT NULL DEFAULT '',
  status SMALLINT NOT NULL DEFAULT 1,
  issued_at TIMESTAMPTZ NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL,
  revoked_at TIMESTAMPTZ NOT NULL DEFAULT '1970-01-01T00:00:00Z',
  created_at TIMESTAMPTZ NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL,
  deleted SMALLINT NOT NULL DEFAULT 0
);

CREATE UNIQUE INDEX uk_gateway_refresh_token_id ON gateway_refresh_token(refresh_token_id);
CREATE UNIQUE INDEX uk_gateway_refresh_token_jti ON gateway_refresh_token(token_jti);
CREATE INDEX idx_gateway_refresh_token_account ON gateway_refresh_token(account_id, status, deleted);
CREATE INDEX idx_gateway_refresh_token_user ON gateway_refresh_token(user_id, status, deleted);
CREATE INDEX idx_gateway_refresh_token_expire ON gateway_refresh_token(expires_at, status, deleted);
```

状态：

- 1 ACTIVE
- 2 ROTATED
- 3 REVOKED
- 4 EXPIRED

说明：

- `token_hash` 保存 `HMAC-SHA256(refresh_token_hmac_secret, refresh_token_random_secret)`。
- 禁止保存 refresh token 明文。
- `refresh_token_secret` 与账号 HMAC secret 分开配置。

### 12.5 不建表说明

- 不建 `gateway_jwt_blacklist` 表。access token blacklist 只放 Redis。
- 暂不建登录审计表。MVP 使用结构化日志、traceId 和指标排查。

## 13. 缓存设计

Redis key 统一前缀通过 Nacos 配置项 `gateway.redis.key-prefix` 下发，默认值为 `dating:mobile-gateway`。代码禁止硬编码前缀；本地开发可以使用默认值，生产环境以 Nacos 配置为准。下表用 `{redis_prefix}` 表示该配置值。

| 场景 | Key | TTL | 说明 |
|---|---|---|---|
| 限流 | `{redis_prefix}:ratelimit:{dimension}:{key}:{window}` | 窗口期 + 10s | IP / account / device / path |
| 手机验证码 | `{redis_prefix}:sms-code:{phone_hash}` | 5m | 只保存验证码 hash |
| 手机验证码冷却 | `{redis_prefix}:sms-cooldown:{phone_hash}` | 60s | 防止频繁发送 |
| 登录失败计数 | `{redis_prefix}:login-fail:{type}:{principal_hash}` | 15m | 防暴力尝试 |
| JWT 黑名单 | `{redis_prefix}:jwt:blacklist:{jti}` | access token 剩余 TTL | 仅 Redis 保存 |
| refresh token 会话 | `{redis_prefix}:refresh:{jti}` | refresh token 剩余 TTL | 加速刷新校验 |
| Google JWKS | `{redis_prefix}:google:jwks:{kid}` | 12h | 可选，本地内存优先 |
| 账号短缓存 | `{redis_prefix}:account:{account_id}` | 5m | 可选 |
| 设备短缓存 | `{redis_prefix}:device:{device_id}` | 5m | 可选 |

要求：

- 所有 Redis key 必须有 TTL。
- Redis 不是最终数据源，验证码和 blacklist 除外。
- refresh token 以 PostgreSQL 为准，Redis 只是加速。
- 手机验证码只保存在 Redis，校验成功后立即删除。
- Redis 不可用时，手机验证码登录 / 注册 fail closed。
- Redis blacklist 丢失时，已退出的 access token 可能在剩余 TTL 内继续有效；该风险由 15 分钟 access token 短 TTL 接受。
- JwtAuthFilter 校验 Redis blacklist 时，如果 Redis 不可用，MVP 选择 fail closed，返回 `10508`。
- 限流 Redis 异常和 blacklist Redis 异常分开处理。

## 14. 异步和消息设计

MVP 不引入 MQ。

原因：

- 当前网关认证流程可用本地事务 + 事务外 gRPC 调用闭合。
- user-service 初始化接口必须按 `user_id` 幂等，网关失败后通过下一次登录重试。
- 引入 MQ 会增加 Topic、消费幂等、死信、补偿和运维复杂度，不符合当前 MVP 克制范围。

后续如果需要异步初始化、审计、风控或通知，需要单独确认 RocketMQ 引入范围。

## 15. 文件和对象存储设计

MVP 不直接使用 MinIO 或对象存储。

说明：

- 网关不接收业务文件上传。
- 网关不直接读写其他服务 bucket。
- 后续如需头像、帖子图片、临时文件等能力，必须通过 owner service 的 gRPC 获取 presigned URL 或 object key。

## 17. 核心业务流程

### 17.1 手机验证码登录 / 注册

```text
1. 校验手机号格式和限流。
2. 发送验证码，Redis 保存验证码 hash。
3. 登录时校验验证码。
4. 使用 PHONE + phone_hash 执行 findOrCreateAccount。
5. 如果 user_register_status=0，调用 user-service 初始化。
6. 初始化成功后更新 user_register_status=1。
7. 签发 access token 和 refresh token。
```

约束：

- 手机号不落库明文。
- 验证码不落库明文。
- 验证码校验成功后立即删除。

### 17.2 Google 登录 / 注册

```text
1. 客户端提交 google_id_token。
2. 解析 header.kid。
3. 从本地 JWKS 缓存获取公钥。
4. kid miss 时刷新 Google JWKS。
5. 校验签名、issuer、audience、exp。
6. 提取 Google subject。
7. 使用 GOOGLE + subject_hash 执行 findOrCreateAccount。
8. 如果 user_register_status=0，调用 user-service 初始化。
9. 签发 access token 和 refresh token。
```

### 17.3 设备号快速登录 / 注册

```text
1. 客户端提交 device_key。
2. 校验 device_key 格式。
3. 按 IP + device_key_hash 限流。
4. 查询 gateway_device。
5. 如果设备存在且禁用，返回 10401。
6. 如果设备存在且正常，使用其 account_id、user_id 登录。
7. 如果设备不存在，创建 DEVICE 类型账号和 gateway_device。
8. 如果 user_register_status=0，调用 user-service 初始化。
9. 签发 access token 和 refresh token。
```

核心规则：

- 同一个 `device_key_hash` 永远返回同一个 `user_id`。
- 不同 `device_key_hash` 首次快速登录生成不同 `user_id`。
- 不做设备快登账号升级为手机号 / Google 账号。

### 17.4 JWT 验签

```text
1. JwtAuthFilter 读取 Authorization Bearer token。
2. JwtService 校验签名、issuer、exp、typ、alg。
3. 查询 Redis blacklist。
4. Redis blacklist 不可用时返回 10508。
5. 通过后把 user_id、account_id、device_id、trace_id 放入请求上下文。
6. REST 转 gRPC 时透传 metadata。
```

### 17.5 refresh token 刷新

```text
1. 解析 refresh token 中的 jti 和 random secret。
2. 按 jti 查询 gateway_refresh_token，校验 token_hash、expires_at 和状态。
3. 条件更新旧 token：ACTIVE -> ROTATED。
4. 影响行数不是 1，返回 10506。
5. 插入新的 gateway_refresh_token。
6. 签发新的 access token 和 refresh token。
7. 事务提交后更新 Redis refresh 缓存。
```

## 19. 事务设计

原则：

- 事务只放在 Service 层。
- 本地事务只写 `mobile-gateway` 自己的 PostgreSQL 表。
- 事务内不调用 gRPC。
- 事务内不发 MQ。
- 事务内不调第三方 API。

登录 / 注册并签发 refresh token：

```text
1. 事务外完成手机验证码 / Google / 设备号凭据校验。
2. 事务 A 内 findOrCreateAccount；新账号写 user_register_status=0。
3. 设备快登时事务 A 内按需 findOrCreateDevice。
4. 事务 A 提交。
5. 如果是新账号或 user_register_status=0，事务外调用 user-service 初始化。
6. user-service 返回成功后，事务 B 更新 user_register_status=1。
7. 事务 C 写 gateway_refresh_token。
8. 事务 C 提交后写 Redis refresh 缓存。
```

失败处理：

- user-service 初始化失败时，不签发 token，返回 `10703`。
- 已创建的 `gateway_account` 不回滚，保留 `user_register_status=0`。
- 下一次登录按第一次进入重试初始化。

refresh token 刷新事务：

```sql
UPDATE gateway_refresh_token
SET status = 2, updated_at = now()
WHERE token_jti = :old_jti
  AND status = 1
  AND deleted = 0;
```

影响行数为 1 才允许插入新 refresh token。

## 20. 幂等设计

- `account_type + account_key_hash + deleted` 唯一。
- `device_key_hash + deleted` 唯一。
- `token_jti` 唯一。
- 账号创建唯一键冲突后重新查询账号并按登录处理。
- 设备创建唯一键冲突后按 `device_key_hash` 重新查询设备，并使用设备已绑定的 `account_id`、`user_id` 登录。
- 禁止同一个 `device_key_hash` 生成第二个 `user_id`。
- user-service 初始化接口必须以 `user_id` 为幂等键。
- refresh token 轮换时，旧 token 重复使用返回 `10506`。
- logout 重复调用返回成功或已退出，不抛系统异常。

## 21. 权限和安全设计

- 登录接口公开，但必须限流。
- 业务接口必须经过 `JwtAuthFilter`。
- access token 本地验签，不调用下游服务。
- Redis blacklist 命中时拒绝请求。
- Redis blacklist 不可用时 fail closed。
- 手机号、Google subject、设备号统一使用 HMAC-SHA256。
- refresh token 入库只保存 HMAC hash。
- JWT `alg` 固定为 `RS256`。
- 私钥 / 公钥使用 PEM 或 Base64 PEM 形式通过环境变量注入。
- MVP 不配置 `kid`。
- 日志禁止打印 JWT、refresh token、验证码、手机号、Google token、设备原始 ID、密钥。
- 设备号快速登录属于低信任登录方式，但 MVP 不做敏感接口强制绑定手机号或 Google。

## 23. 可靠性设计

- access token blacklist 只查 Redis。
- Redis blacklist 丢失风险通过 access token 短 TTL 接受。
- Redis blacklist 校验不可用时，JwtAuthFilter fail closed，返回 `10508`。
- refresh token 以 PostgreSQL 为准，Redis 只做缓存。
- 手机验证码依赖 Redis，Redis 不可用时手机验证码登录 / 注册 fail closed。
- Google JWKS 使用本地缓存，kid miss 时刷新，刷新失败 fail closed。
- user-service 注册 / 初始化不可用时，首次注册 fail closed，不签发 token。
- gRPC 调用必须设置 deadline。
- BFF 聚合必须设置总超时和单调用超时。
- Redis 限流异常按接口风险 fail open / fail closed。
- JWT 密钥加载失败时服务不应健康。
- PostgreSQL 不可用时，签发和刷新 token fail closed。

## 24. 兜底方案

| 场景 | 可能失败点 | 主方案 | 兜底方案 | 是否重试 | 是否需要人工介入 | 最终状态 | 用户感知 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 手机验证码发送 | 短信供应商超时 / 失败 | `SmsProviderClient` 发送，Redis 保存验证码 hash | 返回 `10000` 或供应商映射码；保留发送失败日志和 traceId，不写登录态 | 可按接口限流后重试 | 否 | 未登录 | 提示稍后重试 |
| 手机验证码校验 | Redis 不可用 | Redis 校验验证码 hash | fail closed，返回验证码不可用类错误 | 用户稍后重试 | 否 | 未登录 | 提示稍后重试 |
| Google 登录 | JWKS kid miss 且刷新失败 | 本地缓存优先，kid miss 刷新 JWKS | 返回 `10300`，不创建账号 | 用户稍后重试 | 否 | 未登录 | 提示 Google 登录失败 |
| user-service 初始化 | gRPC 超时 / 失败 | 本地事务提交后调用 `RegisterOrInitialize` | 不签发 token，保留 `user_register_status=0`，下次登录按第一次进入重试 | 是，下次登录重试 | 持续失败需排查告警 | 认证账号存在但不可登录 | 提示注册初始化失败 |
| 账号并发注册 | 唯一索引冲突 | `findOrCreateAccount` 插入 | 捕获冲突后重新查询并按登录处理 | 自动处理 | 否 | 单账号唯一 | 无感知或正常登录 |
| 设备快登并发注册 | `device_key_hash` 唯一冲突 | 先查设备，不存在则创建 | 冲突后按 `device_key_hash` 重查设备，使用已绑定 `user_id` | 自动处理 | 否 | 一个设备一个用户 | 正常登录 |
| refresh token 并发刷新 | 多请求同时刷新旧 token | 条件更新 ACTIVE -> ROTATED | 影响行数非 1 返回 `10506` | 客户端重新登录 | 否 | 只有一个新 refresh token | 提示登录态失效 |
| access token 退出 | Redis blacklist 写入失败 | 写入 Redis blacklist，TTL 为剩余有效期 | 返回失败，不声明退出成功；refresh token 撤销按本地事务处理 | 可重试退出 | 持续失败需排查 Redis | 退出未完全生效 | 提示稍后重试 |
| JWT blacklist 校验 | Redis 不可用 | JwtAuthFilter 查询 Redis | fail closed，返回 `10508` | 用户稍后重试 | Redis 持续不可用需告警 | 请求拒绝 | 提示服务暂不可用 |
| BFF 聚合 | 非必需下游失败 | 必需数据整体失败，非必需数据 partial | 非必需数据返回空值和 partial errors；必需数据失败返回业务错误 | 可由用户刷新 | 否 | 响应降级或失败 | 页面局部缺失或提示重试 |
| PostgreSQL 不可用 | 账号 / refresh 写入失败 | 本地事务写库 | fail closed，不签发 token | 用户稍后重试 | 需要告警处理 | 未登录或刷新失败 | 提示稍后重试 |
| JWT 密钥加载失败 | 环境变量缺失 / 格式错误 | 启动加载私钥 / 公钥 | 服务健康检查失败，不接流量 | 启动修复后重试 | 是 | 服务不可用 | 用户无法访问 |
| 固定 worker-id 风险 | 多实例误部署生成 ID | MVP 只允许一个生成 ID 实例 | 部署检查和告警；发现冲突需停止新增实例 | 否 | 是 | 保护 ID 唯一性 | 无直接感知或服务不可用 |

## 26. 本地开发和部署

本地配置示例：

```yaml
server:
  port: 8080

spring:
  application:
    name: mobile-gateway
  threads:
    virtual:
      enabled: true
  datasource:
    url: jdbc:postgresql://localhost:5432/dating_gateway
  data:
    redis:
      host: localhost
      port: 6379

gateway:
  redis:
    key-prefix: dating:mobile-gateway # 本地默认值，生产环境从 Nacos 下发
  id-generator:
    worker-id: 1
    datacenter-id: 1
  hash:
    version: 1
    secret: ${ACCOUNT_HASH_SECRET}
  jwt:
    issuer: dating-mobile-gateway
    algorithm: RS256
    access-token-ttl-seconds: 900
    refresh-token-ttl-seconds: 2592000
    private-key: ${JWT_PRIVATE_KEY}
    public-key: ${JWT_PUBLIC_KEY}
    refresh-token-secret: ${REFRESH_TOKEN_HASH_SECRET}
  cors:
    allowed-origins:
      - http://localhost:3000
  rate-limit:
    default-window-seconds: 60
    default-max-requests: 120
  sms:
    code-ttl-seconds: 300
    cooldown-seconds: 60
  google:
    client-id: ${GOOGLE_CLIENT_ID}
    jwks-cache-ttl-seconds: 43200
    http-timeout-ms: 2000
```

部署约束：

- MVP 固定 `worker-id=1`、`datacenter-id=1`。
- MVP 只部署一个负责生成雪花 ID 的 `mobile-gateway` 实例。
- 扩展多实例前，必须先设计 worker-id 分配、冲突检测和启动失败策略。

提交前验证：

```bash
mvn -B -ntp clean package
```

测试重点：

- 雪花算法生成 `user_id`、`account_id`、`device_id`。
- 手机验证码发送、校验、登录 / 注册。
- Google token 校验、JWKS 缓存、kid miss、audience 不匹配。
- 同一个 device_key 重复快速登录返回同一个 user_id。
- 不同 device_key 快速登录生成不同 user_id。
- 首次注册后调用 user-service 注册 / 初始化流程。
- user-service 初始化失败时不签发 token，并保留 `user_register_status=0`。
- JWT `alg` 固定为 RS256，错误 alg / 错误公钥必须拒绝。
- refresh token 数据库不保存明文，只保存 HMAC hash。
- Redis blacklist 不可用时返回 `10508`。
- refresh token 条件更新、并发刷新和重复使用。
- 限流、CORS、traceId、REST/gRPC、BFF 字段裁剪。
- P95 / P99 压测指标。
