# 阶段 2：设备快速登录最小闭环

## 1. 阶段目标

完成 `/api/v1/auth/login/device` 最小认证闭环：客户端提交 `device_key` 后，网关完成限流、HMAC、账号 / 设备创建或查询、全局 `user_id` 生成、user-service 初始化、JWT access token 签发、refresh token 持久化和统一返回。

这是第一条完整登录路径，用于尽早验证 `gateway_account`、`gateway_device`、`gateway_refresh_token` 三张核心表和 token 主链路。

## 2. 阶段类型

中耦合纵向切片。

## 3. 输入依据

- 最终方案第 9.1 章登录 / 注册链路。
- 最终方案第 12.2、12.3、12.4 章数据模型。
- 最终方案第 16.2 章认证接口。
- 最终方案第 17.3 章设备号快速登录 / 注册。
- 最终方案第 19、20 章事务和幂等。

## 4. 输出结果

- `gateway_account`、`gateway_device`、`gateway_refresh_token` migration。
- `GatewayAccountEntity`、`GatewayDeviceEntity`、`GatewayRefreshTokenEntity`、Mapper 和 Manager。
- `/api/v1/auth/login/device` REST 接口。
- `DeviceLoginService`、`AuthService`、`JwtService`、`RefreshTokenManager` 的最小实现。
- 首次登录调用 user-service `RegisterOrInitialize`，成功后更新 `user_register_status=1`。
- 同一个设备重复登录返回同一个 `user_id`；不同设备生成不同 `user_id`。

## 5. 前置依赖

- 阶段 1：必要工程基础。

## 6. 耦合度说明

- 耦合度等级：中耦合。
- 耦合度总分：6。
- 排序理由：依赖 PostgreSQL、Redis、JWT、user-service gRPC mock，但没有短信供应商和 Google 第三方依赖，是最低成本的完整认证闭环。

## 7. 数据库低耦合说明

本阶段创建三张表，因为设备登录成功必须同时落地账号、设备和 refresh token：

- `gateway_account`：认证账号和全局 `user_id`。
- `gateway_device`：设备快登身份，一个 `device_key_hash` 只对应一个 `user_id`。
- `gateway_refresh_token`：登录成功必须持久化 refresh token 会话。

所有表保留内部 `id BIGSERIAL PRIMARY KEY`，业务操作只使用 `account_id`、`device_id`、`refresh_token_id`、`user_id`。

## 10. 详细任务拆分

### 任务 2.1：核心认证表 migration 和单表访问

- 任务编号：2.1
- 任务名称：核心认证表 migration 和单表访问
- 所属阶段：阶段 2
- 阶段类型：中耦合纵向切片
- 业务闭环：设备登录所需账号、设备和 refresh token 可落库。
- 涉及文件：migration、Entity、Mapper。
- 作用：提供认证域持久化基础。
- 前置条件：阶段 1。
- 被阻塞于：阶段 1。
- 是否阻塞后续：是。
- 耦合度说明：依赖 PostgreSQL。
- 数据库变更：创建 `gateway_account`、`gateway_device`、`gateway_refresh_token` 及唯一索引。
- API / gRPC / MQ 契约：无。
- 实现要点：字段使用 `xxx_id`；时间字段 `TIMESTAMPTZ`；原则上 `NOT NULL`；历史 migration 合并后只新增不修改。
- 事务 / 幂等 / 一致性：唯一索引用于幂等：`account_type + account_key_hash + deleted`、`device_key_hash + deleted`、`token_jti`。
- 异常和权限：唯一键冲突不直接暴露数据库异常，由 Manager 重查处理。
- 验收标准：migration 可重复在空库执行；三张表字段和索引符合最终方案；Mapper 可按业务 ID 查询。
- 验证方式：Repository / Testcontainers 测试。
- 是否 MVP 必做：是。
- 建议执行方式：AI 生成初稿，人工审查 SQL。

### 任务 2.2：账号与设备 find-or-create 幂等

- 任务编号：2.2
- 任务名称：账号与设备 find-or-create 幂等
- 所属阶段：阶段 2
- 阶段类型：中耦合纵向切片
- 业务闭环：同一个 `device_key_hash` 永远映射到同一个 `account_id` 和 `user_id`。
- 涉及文件：`GatewayAccountManager.java`、`GatewayDeviceManager.java`
- 作用：封装账号和设备创建、冲突重查、禁用状态判断。
- 前置条件：任务 2.1。
- 被阻塞于：任务 2.1。
- 是否阻塞后续：是。
- 耦合度说明：依赖 PostgreSQL 和雪花 ID。
- 数据库变更：无新增表，写入阶段 2 表。
- API / gRPC / MQ 契约：无。
- 实现要点：设备不存在时创建 DEVICE 类型账号、生成 `account_id`、`device_id`、`user_id`；唯一键冲突后按 hash 重查。
- 事务 / 幂等 / 一致性：事务只包本地表写入；禁止事务内调用 gRPC。
- 异常和权限：设备禁用返回 `10401`，设备号无效返回 `10400`。
- 验收标准：同一 `device_key` 并发登录最终只生成一个 `user_id`；不同 `device_key` 生成不同 `user_id`。
- 验证方式：Service 并发测试。
- 是否 MVP 必做：是。
- 建议执行方式：AI 辅助修改。

### 任务 2.3：JWT access token 签发和 refresh token 首次持久化

- 任务编号：2.3
- 任务名称：JWT access token 签发和 refresh token 首次持久化
- 所属阶段：阶段 2
- 阶段类型：中耦合纵向切片
- 业务闭环：登录成功后返回 access token 和 refresh token。
- 涉及文件：`JwtService.java`、`RefreshTokenManager.java`、`LoginTokenVO.java`
- 作用：生成 RS256 access token、SecureRandom refresh token，持久化 refresh token random secret 的 HMAC hash。
- 前置条件：任务 2.1、2.2。
- 被阻塞于：任务 2.1、2.2。
- 是否阻塞后续：是。
- 耦合度说明：依赖 JWT 密钥、PostgreSQL、Redis refresh 缓存。
- 数据库变更：写入 `gateway_refresh_token`。
- API / gRPC / MQ 契约：登录成功返回 `access_token`、`refresh_token`、`token_type=Bearer`、`expires_in=900`。
- 实现要点：JWT `alg` 固定 RS256；MVP 不使用 `kid`；refresh token 使用 `rt_<jti>.<random_secret>` 格式，入库只保存 random secret 的 HMAC hash，禁止保存明文。
- 事务 / 幂等 / 一致性：refresh token 写库成功后再写 Redis refresh 缓存。
- 异常和权限：密钥不可用返回 `10507` 或启动失败。
- 验收标准：access token 可用公钥验签；refresh token 明文和 random secret 不出现在数据库和日志；Redis refresh key 带统一前缀和 TTL。
- 验证方式：单元测试、数据库断言、Redis 断言。
- 是否 MVP 必做：是。
- 建议执行方式：人工实现核心密钥处理，AI 辅助测试。

### 任务 2.4：设备快速登录 API 闭环

- 任务编号：2.4
- 任务名称：设备快速登录 API 闭环
- 所属阶段：阶段 2
- 阶段类型：中耦合纵向切片
- 业务闭环：调用 `/api/v1/auth/login/device` 获得可验签的 access token 和已持久化的 refresh token。
- 涉及文件：`AuthController.java`、`DeviceLoginService.java`、DTO / VO。
- 作用：提供第一个用户可见登录入口。
- 前置条件：任务 2.2、2.3。
- 被阻塞于：任务 2.2、2.3。
- 是否阻塞后续：是。
- 耦合度说明：依赖 DB、Redis、user-service mock。
- 数据库变更：写账号、设备、refresh token。
- API / gRPC / MQ 契约：`POST /api/v1/auth/login/device`。
- 实现要点：校验 `device_key` 格式；按 IP + `device_key_hash` 限流；调用 user-service 初始化成功后才签发 token。
- 事务 / 幂等 / 一致性：本地事务 A 提交后事务外调用 user-service，再事务 B 更新 `user_register_status=1`，事务 C 写 refresh token。
- 异常和权限：初始化失败返回 `10703`，不签发 token，保留 `user_register_status=0`。
- 验收标准：首次设备登录返回 token；再次同设备登录返回同一 `user_id`；不同设备返回不同 `user_id`。
- 验证方式：HTTP API 集成测试。
- 是否 MVP 必做：是。
- 建议执行方式：AI 辅助修改。

### 任务 2.5：user-service 初始化失败兜底

- 任务编号：2.5
- 任务名称：user-service 初始化失败兜底
- 所属阶段：阶段 2
- 阶段类型：中耦合纵向切片
- 业务闭环：首次注册初始化失败时不发 token，下次登录按第一次进入重试。
- 涉及文件：`AuthService.java`、`UserGrpcClient.java`、测试。
- 作用：落实网关不参与 user-service 用户资料事务的边界。
- 前置条件：任务 2.4。
- 被阻塞于：任务 2.4。
- 是否阻塞后续：是。
- 耦合度说明：依赖 user-service gRPC mock。
- 数据库变更：`gateway_account.user_register_status` 保持 `0`，成功后更新为 `1`。
- API / gRPC / MQ 契约：`RegisterOrInitialize` 失败映射 `10703`。
- 实现要点：事务内不调用 gRPC；失败不回滚已创建账号；重试登录时再次初始化。
- 事务 / 幂等 / 一致性：user-service 必须按 `user_id` 幂等；网关重试不会生成第二个 `user_id`。
- 异常和权限：超时 `10701`，异常 `10702`，业务初始化失败 `10703`。
- 验收标准：mock 初始化失败时接口不返回 token；数据库账号存在且 `user_register_status=0`；下一次 mock 成功后返回 token 并更新状态为 `1`。
- 验证方式：HTTP + gRPC mock 集成测试。
- 是否 MVP 必做：是。
- 建议执行方式：AI 辅助修改。

## 12. 验收标准

- migration 后存在 `gateway_account`、`gateway_device`、`gateway_refresh_token` 三张表和最终方案要求的索引。
- `POST /api/v1/auth/login/device` 合法请求返回 `code=0`、`access_token`、`refresh_token`、`token_type=Bearer`、`expires_in=900`。
- 数据库保存 `account_id`、`device_id`、`user_id`、`refresh_token_id`，业务编号统一使用 `xxx_id`。
- 同一个 `device_key` 重复登录返回同一个 `user_id`。
- 不同 `device_key` 首次登录生成不同 `user_id`。
- user-service 初始化失败时返回 `10703`，不签发 token，保留 `user_register_status=0`。
- refresh token 明文不进入数据库和日志。

- user-service mock 成功即代表用户资料初始化成功，不在网关内写用户资料字段。
